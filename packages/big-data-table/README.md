# 大数据列表/表格渲染

## 决策层（第一步：判断走哪条路）

| 你的约束 | 选哪个 | 原因 |
|---|---|---|
| DOM 可以裁剪，用户只是滚动浏览 | 虚拟滚动 + Worker | 只渲染可视区，DOM 数量可控 |
| DOM 必须完整（Ctrl+F / 无障碍 / 打印） | 时间切片 | 所有行都得真实存在，但分批渲染不卡 UI |

> 注意：以上只是**渲染层**。搜索/排序/筛选的计算阻塞是另一件事，
> 无论走哪条路，耗时计算都要丢进 Web Worker。

## 方案 A：虚拟滚动（DOM 可裁剪）

实现见 `src/useVirtualScroll.ts` + `src/useBigDataTable.ts` + `src/table.worker.ts`。

### 结论

- 只渲染可视区 `[start, end]`，上下各留约 20 行缓冲
- 筛选 / 排序放 Worker，**只回传匹配到的 rowId 列表**，不回传完整对象（省通信开销）
- 勾选状态用 `Set`（O(1)），全选/半选用 `isAllSelected + excludedIds` 标志位推导，不遍历
- 勾选**绑定稳定的 rowId，绝不绑数组下标**（排序/筛选会打乱下标）

### 什么时候升级

- 十万级：上面的够用
- 百万级：加 IndexedDB 分层（存储层落地、渲染时按需取详情、只留 ID 序列在内存）

### 坑

- 虚拟滚动只解决 DOM 渲染，**不解决计算阻塞**——别以为上了虚拟滚动就完事
- 勾选状态绑定下标 = 排序后错乱
- 高频输入每字符都全量 filter → 先 300ms 防抖，再丢 Worker
- 高频检索可预建「关键词 → rowId」倒排索引，O(N) 降成近似 O(1)
- **Worker 会静默失败**：内嵌 webview（IDE 内置浏览器）/ CSP 环境里，Worker 可能不报错也不响应。
  必须做兜底（本实现：创建失败 / onerror / 3 秒超时 → 自动回退主线程并提示），否则成了"灵异 bug"

## 方案 B：时间切片（DOM 必须完整）

实现见 `src/useTimeSlicing.ts`。

### 结论

- 分批追加数据，每批 20~50 条，批间 `await setTimeout(0)` 让出主线程
- 关键坑：简单 setTimeout 分批有**竞态**——旧搜索还在追加，新搜索已经开始，
  结果互相污染。要靠「最新一次请求胜出」的自增 runId（本仓库实现）或 vue-asyncx，
  新搜索自动作废旧任务

### 坑

- 用 setTimeout 分批但没处理竞态 = 结果闪烁 + 列表串味，比卡顿更难查
- debounce 不能根治竞态，它只减少触发次数，不解决「两次异步过程重叠」

## 配置项（可参数化）

| 配置项 | 默认值 | 说明 |
|---|---|---|
| 缓冲行数 `buffer` | 20 | 可视区上下额外渲染的行数 |
| 防抖延迟 | 300ms | 高频输入的拦截时间 |
| 时间切片 `chunkSize` | 50 | 每批追加的条数 |
| `useWorker` | false | 数据量小直接主线程，省序列化开销 |
| 行高 `rowHeight` | 40 | 固定行高；动态行高复杂度翻倍 |

> 我要实现一个大数据量表格/列表，遵循以下规则：
> 1. 先判断 DOM 是否必须完整（是否需要 Ctrl+F 搜索、打印、无障碍朗读）：
>    - 可裁剪 → 虚拟滚动：只渲染可视区 [start, end]，上下各留 20 行缓冲，
>      用撑高容器 + translateY 偏移模拟完整滚动条；
>    - 必须完整 → 时间切片：分批追加（每批 50 条），批间 `await setTimeout(0)` 让出主线程，
>      并用自增 runId 实现「最新请求胜出」防止新旧任务竞态污染列表。
> 2. 渲染层之外，筛选/排序/搜索等耗时计算一律放 Web Worker，且只回传匹配的 rowId 列表、
>    不回传完整对象；数据量小（几百条内）直接主线程算，省序列化开销。
> 3. 勾选状态用 Set 存储，绑定稳定的业务 id，绝不绑数组下标；全选用
>    isAllSelected 布尔 + excludedIds Set 推导，不遍历全量数据。
> 4. 高频搜索输入先做 300ms 防抖，再触发检索。
