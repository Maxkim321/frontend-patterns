> 智能报价交互层的可运行版本：分步填报价要素（品类 → 规格数量 → 折扣条件）→
> 提交后 Agent 检索规则计算（模拟延迟）→ 报价明细 + 逐字流式的生成式说明。
> 每步有引导与校验（不填必填项「下一步」会被拦截），结果页可返回编辑、数据保留。

## 出处说明

源自洛阳经济智能体项目（quotation-agent）的智能报价模块——源码中 `SmartQuoteView.vue`
是规划中的占位页（代码注释原话："后续可用于报价单、参数选择和结果对比"），向导交互层
当时未落地；本方案是该交互层的**完整实现沉淀**，demo 即按业务场景做的可运行版本。

## 面试口径（R2：智能报价你做了什么？）

> 我参与前端交互层：用户走的是表单向导——按步骤填报价要素（品类、规格、数量、折扣条件），
> 每步有引导和校验；填完提交，服务端 Agent 检索规则计算，前端展示报价明细加一段生成式说明
> （流式输出）。Agent 的编排逻辑在服务端，我负责交互和结果渲染，和后端配合。

## 决策层（为什么分步向导）

报价要素 10+ 字段且有序依赖，一页长表单压迫感强、易漏填；分步向导按认知顺序拆步
（品类 → 规格数量 → 折扣），每步只关注 1~2 个决策，校验边界清晰。
报价是"结构化输入 + 规则计算"——Agent 规则检索需要确定的字段名和类型，分步向导保证提交数据结构化。

## 结论

| 模块 | 职责 |
|---|---|
| `useWizard.ts` | 步索引、数据聚合、分步校验、提交状态机（框架无关） |
| `FormWizard.vue` | 步骤条 + schema 渲染当前步 + 校验拦截 + 提交防重；`#result` / `#step-<index>` 插槽外放 |

## 原理讲解

### 校验边界：只校验当前步

点「下一步」才校验当前步字段（required + 自定义 validate），错误字段级跟随控件——
用户在第 2 步不该被第 3 步的必填项拦住。

### 数据贯穿，最后提交

所有步骤共享同一个 data，最后一步才整体提交；`editFrom` 保留数据回到任意已填步骤，
状态回 idle，改完重新提交。

### 提交状态机防重复

`idle → submitting → done/error`：submitting 期间按钮 loading 且 submit 直接返回 false
（防同一单提交两次）；reject 显示原因，数据不丢可直接重试。

### 生成式说明的流式渲染

提交成功后 Agent 返回的说明逐字流式渲染（demo 打字机模拟；真实项目接 SSE，
解析器与「AI 对话组件」方案同一条 `consumeSSEStream` 链路——workspace 包拆分的复用收益）。

## 坑

- **整表校验** → 用户在第 1 步被第 3 步的必填拦住
- **每步单独提交** → 中间态脏数据进后端，还得做草稿/作废
- **提交不加状态机** → 双击 = 同一单计算两次
- **返回编辑丢数据** → 结果页"返回修改"若 reset 了 data，用户全部重填
- **步骤条只能前进** → 改第 1 步要一路"上一步"点回去；已完成步骤应可点击直达
- **打字机定时器不清理** → 组件卸载后 setInterval 泄漏
- **校验错误只弹 toast** → 用户找不到哪错了；错误必须跟随控件

## 配置项

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `steps[].fields[].type` | input | input / textarea / select / number |
| `fields[].required` | false | next 时校验当前步必填 |
| `fields[].validate` | 无 | 业务校验，返回 true 或错误字符串 |
| `#result` 插槽 | 无 | 结果区业务渲染（明细 + 生成式说明） |
| `#step-<index>` 插槽 | 无 | 接管某一步渲染 |
