## 原理讲解：为什么卡，为什么这么做

### 先把「卡」拆成两件独立的事

| 层 | 卡的原因 | 解法 |
|---|---|---|
| **渲染层** | DOM 节点太多：1 万行 × 每行 6 个格子 ≈ 7 万+ 节点，排版/绘制/内存全线吃紧 | 别渲染看不见的（虚拟滚动）或分批渲染（时间切片） |
| **计算层** | 主线程被同步计算占死：一次 1 万行的 filter/sort 轻松吃掉几十到几百 ms，而浏览器一帧只有约 16ms 预算（60fps） | 耗时计算丢 Web Worker |

这两层是**独立的**：只做虚拟滚动、搜索照样卡死；只做 Worker、滚动照样掉帧。所以结论是两个都要做。

### 虚拟滚动怎么工作的

三个配合的元素：固定高度的视口 + 一个撑高的空容器（让滚动条长度等于"假装渲染了全部"）+ 一个 `translateY` 偏移层。

滚动时只做一件事：`scrollTop ÷ 行高` 算出当前可视区的 `[startIndex, endIndex]`，只渲染这个区间，上下各留 20 行缓冲。

**效果（本 demo 实测）**：1 万行数据，DOM 里真实存在的行**始终只有 ~34 个**（DevTools 的 Elements 面板可直接数）——量级差 2~3 个数量级。为什么需要缓冲行：快速滚动时给渲染留出时间，否则可视区边缘会露白。

### 为什么计算必须丢 Worker，且只传 ID

- 主线程的职责是响应用户：输入、滚动、点击。同步计算哪怕只占 100ms，用户就体感"卡了一下"；Worker 是独立线程，算多久都不影响主线程帧率
- **只回传 rowId 列表、不回传完整对象**：线程间通信用结构化克隆，大对象克隆很贵；1 万个 ID 的数组比 1 万个对象小几个数量级
- 坑：数据量小（几百条）时，worker 的序列化开销反而比直接算更慢——所以 `useWorker` 默认 `false`，量大再开

### 为什么勾选绑 rowId、绝不绑下标

排序/筛选会**重排或裁剪数组**：下标 5 昨天是"张三"，排序后今天变成"李四"，状态全错。`rowId` 是业务身份，永远稳定。配套设计：`Set` 存储（增删查 O(1)），全选用 `isAllSelected + excludedIds` 两个标志推导，不遍历全量数据。

### 时间切片怎么工作的（DOM 必须完整时）

Ctrl+F 只能搜到真实存在的 DOM → 不能虚拟裁剪 → 只能把"一次渲染 1 万行"改造成"一个渲染过程"：每 50 条一批、批间 `setTimeout(0)` 让出主线程。UI 全程有响应，最终 DOM 完整。

关键坑是**竞态**：新搜索开始时，旧搜索还在分批追加，列表被污染。解法是自增 `runId` —— "最新一次请求胜出"，旧任务每批之间检查自己是否过期，过期自动退出。

### 优化效果怎么衡量（别只凭感觉）

1. **DOM 节点数**：Elements 面板数行节点，全量 vs 可视区差 2~3 个数量级
2. **滚动帧率**：Performance 面板录制滚动，看有没有红色长任务（>50ms 的阻塞块）
3. **输入跟手感**：搜索框连续快速输入，看列表是否实时跟随（主线程阻塞最直接的体感）

具体毫秒数因机器和数据而异——别抄别人的数字，在自己页面上录。

### 沉淀本方案时真实踩的坑：Worker 静默失败

内嵌 webview（如 IDE 内置浏览器）里 Worker 可能**静默失败**：不报错、不响应，表格直接空白且无任何异常。所以本实现的 Worker 有三层兜底：**创建失败 / 加载报错 / 3 秒超时** → 自动回退主线程计算，并在界面上提示「Worker 不可用」。任何 Worker 方案都应该有这个兜底，否则在别人的环境里会变成"灵异 bug"。

## 决策层（第一步：判断走哪条路）

| 你的约束 | 选哪个 | 原因 |
|---|---|---|
| DOM 可以裁剪，用户只是滚动浏览 | 虚拟滚动 + Worker | 只渲染可视区，DOM 数量可控 |
| DOM 必须完整（Ctrl+F / 无障碍 / 打印） | 时间切片 | 所有行都得真实存在，但分批渲染不卡 UI |

> 以上只是**渲染层**。搜索/排序/筛选的计算阻塞是另一件事，无论走哪条路都要丢进 Web Worker。

## 方案 A：虚拟滚动（DOM 可裁剪）

代码：`packages/big-data-table/src/useVirtualScroll.ts` + `useBigDataTable.ts` + `table.worker.ts`

### 结论

- 只渲染可视区 `[start, end]`，上下各留约 20 行缓冲
- 筛选/排序放 Worker，**只回传 rowId 列表**，不回传完整对象
- 勾选用 `Set`（O(1)），全选/半选用 `isAllSelected + excludedIds` 标志位推导
- 勾选**绑定稳定的 rowId，绝不绑数组下标**

### 坑

- 虚拟滚动只解决 DOM 渲染，**不解决计算阻塞**
- 勾选绑下标 = 排序后错乱
- 高频输入每字符全量 filter → 先 300ms 防抖，再丢 Worker

## 方案 B：时间切片（DOM 必须完整）

代码：`packages/big-data-table/src/useTimeSlicing.ts`

### 结论

- 分批追加数据，批间 `await setTimeout(0)` 让出主线程
- 用自增 runId 做「最新一次请求胜出」，解决 setTimeout 分批的**竞态**

### 坑

- 分批但不处理竞态 = 结果闪烁 + 列表串味
- debounce 不解决竞态，只减少触发次数

## 配置项

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `buffer` | 20 | 可视区上下额外渲染行数 |
| 防抖延迟 | 300ms | 高频输入拦截时间 |
| `chunkSize` | 50 | 时间切片每批条数 |
| `useWorker` | false | 数据量小直接主线程 |
| `rowHeight` | 40 | 固定行高 |

> 1. 先判断 DOM 是否必须完整（是否需要 Ctrl+F 搜索、打印、无障碍朗读）：

>      并用自增 runId 实现「最新请求胜出」防止新旧任务竞态污染列表。
> 2. 渲染层之外，筛选/排序/搜索等耗时计算一律放 Web Worker，且只回传匹配的 rowId 列表、

> 3. 勾选状态用 Set 存储，绑定稳定的业务 id，绝不绑数组下标；全选用
>    isAllSelected 布尔 + excludedIds Set 推导，不遍历全量数据。
> 4. 高频搜索输入先做 300ms 防抖，再触发检索。
